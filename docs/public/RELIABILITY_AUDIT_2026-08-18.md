# StorageMaster reliability audit — 2026-08-18

> **Dated snapshot.** Findings, evidence, and test counts are as of 2026-08-18, when the schema was at v12. Later schema levels and their behaviour are documented in `ARCHITECTURE.md` and `CODEMAP.md`; this file is deliberately not revised, so it remains a faithful record of that audit.

## Outcome

This audit found and corrected multiple data-loss, false-success, cancellation, persistence, migration, scheduling, updater, and UI-lifecycle defects. The work materially raises StorageMaster's safety and fault tolerance, but it does not claim literal 100% reliability. Filesystems, shell APIs, hardware, process crashes, and untested Windows configurations still impose limits listed below.

Scope covered the managed and Rust scanners, cleanup rules and execution, Smart Cleaner, duplicate detection/deletion/recovery, Windows deletion, SQLite storage and migrations, scheduled/headless execution, updater/release automation, external tools, and high-risk WinUI loading paths.

## Method

- Treated source, tests, schema, and reproducible command output as authoritative; stale prose was corrected separately.
- Established a green baseline before edits: 231 .NET tests passed with one intentional interactive-visual skip; managed and Rust builds/tests passed.
- Used red/green regression tests for reproduced failures. Destructive tests used synthetic temporary files/directories only.
- Kept cleanup/deletion mutations behind `IFileDeleter`; dedicated duplicate restore and updater staging retain their scoped move/staging implementations. Cleanup analysis remained read-only.
- Ran focused tests after each safety batch, then ran whole-tree Release/build/static gates and a real x64 WinUI launch check.
- Did not delete, move, or modify real user files. Live no-follow probes enumerated metadata only under Windows/user temp roots; destructive regressions used synthetic paths. No commit, push, tag, publish, or release was performed.

## Findings and disposition

| ID | Severity | Finding | Disposition |
|---|---|---|---|
| R-01 | Critical | Generic cleanup could pass duplicate members directly to `CleanupEngine`, bypassing keeper revalidation, recovery journal, and dedicated duplicate policy. | Fixed. Generic duplicate rule is not registered and yields no targets. Duplicate removal is exclusive to the dedicated workflow. |
| R-02 | Critical | Raw root checks allowed dot-segment aliases such as `C:\Temp\..`; Recycle Bin flags did not force recycling; recursive permanent traversal had junction-swap exposure. | Fixed. Paths are canonicalized and roots rejected, `FOFX_RECYCLEONDELETE` is required, quarantine destinations are contained, and permanent directory traversal uses no-follow handles held through deletion. |
| R-03 | Critical | Duplicate keeper/member state could change after analysis; a changed keeper could allow deletion of the last valid copy. | Fixed. Keeper and selected members require persisted scan-time identity, attributes, exact UTC metadata, and live strategy signature. Keeper is locked; identity-less legacy rows fail closed; each member is journaled before sequential mutation. |
| R-04 | High | Cached duplicate signatures trusted stored size/time alone and could survive file replacement, disappearance, or attribute changes. | Fixed. Cache reuse now requires live existence, size, timestamp, attributes, and stored/current filesystem identity when the platform provider is present. |
| R-05 | High | Recycle Bin emptying was advertised as recoverable even though Windows emptying is irreversible; risky program-leftover heuristics were enabled and could target whole data directories. | Fixed. Recycle Bin emptying is medium-risk and permanent-only. Program leftovers are disabled, unselected, high-risk, low-confidence, no-follow, descendant-age checked, and Recycle-Bin-only. |
| R-06 | High | Cleanup rule failure, audit failure, cancellation, or unexpected batch failure could hide partial work or prevent other safe analysis results. | Fixed. Rules are isolated; partial outcomes are preserved and audited; audit failures are surfaced without repeating filesystem work. |
| R-07 | Critical | Smart Cleaner recursively followed reparse points, sometimes submitted whole cache directories or unsnapshotted paths, trusted redirected process temp, accepted caller-supplied paths outside known roots, required destructive directory rights even for analysis, and returned only a byte count so partial failure looked successful. | Fixed. It builds explicit plans under canonical OS roots. Read-only analysis uses strong replacement-blocking no-follow guards where available and reports weak fallback as partial; cleanup validation refuses weak guards. Stable identity, per-path outcomes, cancellation, and audit warnings are preserved. |
| R-08 | High | Managed scanner buffers were drained before repository success, so cancellation/write failure could lose rows while terminal counters reported observed rather than persisted work. | Fixed. Batches stay queued until confirmed persistence; terminal counts use confirmed rows; bounded cancellation/failure flushes preserve partial work. |
| R-09 | High | Managed link traversal could loop or cross exclusions through resolved junction targets. | Fixed. Root reparse paths fail when no-follow is requested; physical targets are resolved, excluded, deduplicated, and revalidated before enumeration. |
| R-10 | High | Turbo Scanner persisted zero folder metrics, treated some cancellation/fatal paths as generic failure, followed a root link despite no-follow mode, truncated timestamps/attributes, omitted identity, and could silently use a missing/stale native binary in release validation. | Fixed. Folder metrics and confirmed counts are persisted; cancellation/fatal exits are explicit; link following is opt-in; root ancestry is no-follow validated/locked where Windows permits; one handle supplies exact UTC ticks, raw attributes, and identity; CI/release require the real versioned binary contract. |
| R-11 | High | One shared SQLite connection leaked across repositories and parallel operations, causing nested transactions, lost settings mutations, and unsafe dispose races. | Fixed. Each operation owns an independent configured pooled lease; all repositories dispose leases; settings mutation is one immediate transaction with rollback and cancellation checks. |
| R-12 | High | Multiple contexts/processes could race initial migration, replay stale levels, or lose cross-context writes. Schema v9 also left a quarantine foreign-key deletion conflict. | Fixed. Canonical path coordination covers in-process contexts; migration acquires an immediate writer reservation and re-reads version inside it; schema v10 repairs the FK; cross-context stress and competing-writer regressions pass. |
| R-13 | High | Folder identity allowed Windows case variants to create duplicate rows and inflate aggregates; equal-size largest-file order was unstable. | Fixed in schema v11. Case variants collapse conservatively under normalized uniqueness; upsert semantics avoid double counting; query tie-break is `SizeBytes DESC, FullPath ASC`. |
| R-14 | High | Disabled global/individual scheduled jobs could still execute because the runner ignored persisted policy; cancelled/failed scans could be reported as complete. | Fixed. Core execution policy blocks disabled/unknown jobs; only `Completed` scans return CLI success or set UI completion state. |
| R-15 | High | Task Scheduler command construction and task identity were fragile; any failed query was interpreted as “missing,” so access-denied/transient errors could leave active legacy jobs and create duplicate execution. Sequential legacy cleanup could also mutate one task before a later lookup failed, leaving settings/task state split. | Fixed. Stable hashed names, argument lists, system-safe runner selection, and policy enforcement are used. Every distinct identity is preflighted; OS-task/settings failures trigger compensating rollback, and an incomplete rollback is surfaced explicitly. Only successful inventory proves absence. |
| R-16 | High | Updater could publish an unverified final installer and later launch a replaced file. | Fixed. Download stays in `.part` until length/hash/trust checks pass; launch holds the exact file, rehashes/revalidates trust, then starts the per-user installer unelevated. |
| R-17 | High | Redirected FFmpeg/PowerShell processes could deadlock on pipes, ignore nonzero exit, hang during cancellation, or leave partial preview files. | Fixed. Shared bounded process runner drains pipes, uses argument lists, kills process trees on cancellation, enforces exits, and removes partial output. |
| R-18 | Medium/High | Results and Duplicates asynchronous loads could commit stale session/filter/preview/export/delete state after navigation. | Fixed in source. Generation/lifetime cancellation guards gate commits; initial duplicate loads no longer lose filter refresh; tree-load failures retain retry affordances. Direct WinUI race simulation remains a coverage limit. |
| R-19 | High | Scan timestamps containing `Z` were parsed as local time, while scan-backed cleanup compared them to UTC exactly. Turbo also stored only whole seconds and partial attributes. Unchanged files could fail deletion/cache validation; replacement checks were inconsistent. | Fixed. Every storage repository uses one invariant UTC parser; schema v12 persists full file identity; managed/Turbo scanners populate it; destructive scan consumers require identity; Turbo emits lossless one-handle metadata. Historical rows require rescan. |
| R-20 | High | Duplicate confirmation counted current selections, but long-running execution reread mutable checkbox state. Quarantine moved a file before separately writing terminal journal/catalog state; post-move DB failure could hide recovery location or misreport completed work. | Fixed. UI freezes immutable group/member/method plans and disables editors before confirmation. Quarantine terminal journal + catalog write is transactional; on failure, a terminal journal-only fallback is attempted. If both writes fail, execution stops with exact source/destination in the exception. Post-mutation bookkeeping never retries the filesystem move. |
| R-21 | High | Generic cleanup trusted redirected process temp, preselected medium-risk user-file suggestions, called moved Recycle Bin/quarantine bytes “freed,” and classified zero-byte success plus another failure as total failure. | Fixed. Only canonical OS temp roots are trusted; medium/high suggestions are opt-in; UI distinguishes moved/processed/logical size from reclaimed allocation; outcome status uses successful paths, not positive byte count. |
| R-22 | High | Generic quarantine catalog failure after a successful move remained hidden as success; cancellation arriving after all paths completed could still turn the operation into a cancellation error. | Fixed. Catalog failure produces a partial result with exact manual recovery path; independent bounded recovery recording avoids cancellation suppressing it; fully processed operations remain complete. |
| R-23 | High | Cleanup UI counted `PartialSuccess` as green success, asserted deletion in report titles after failed/partial work, and offered real deletion after an exception or incomplete dry run. It could also ignore a routed scan id or mix suggestions with a session/options selector changed mid-analysis. | Fixed in source. Success/partial/failure counts and colors are distinct; titles describe confirmed outcomes; only a complete all-success preview enables follow-up and permanent delete reconfirms. Routed completed sessions and immutable option snapshots are generation-checked; scope changes cancel and invalidate results. |
| R-24 | High | Scan setup stayed mutable after Start, settings failure could escape before `finally`, singleton initialization could commit stale state, and Space Map cancellation/export I/O could escape async commands. Failed/nonterminal scans were also exposed as ready workspaces. | Fixed in source. Scan config is captured before awaits and controls are gated; all startup work shares the error/finally boundary; navigation/load generations reject stale commits; Space Map funnels superseding loads through one coordinator and surfaces export failures; only completed sessions enable downstream actions. |
| R-25 | High | Settings load/save, history purge, diagnostics export, and scheduler CRUD failures could escape `AsyncRelayCommand` or leave editable defaults after load failure. | Fixed in source. Failed load disables editing and destructive maintenance; command boundaries report full/partial outcomes in-page; diagnostics recording cannot replace the primary updater result. |
| R-26 | High | Choosing and saving `CleanupExecuteSafe` immediately registered enabled unattended deletion without dedicated consent; the runner manufactured `--confirm` internally. | Fixed. New destructive jobs start disabled. Enabling one requires a separate target/rules/schedule/Recycle-Bin confirmation and persists a versioned plan fingerprint. Headless policy denies missing, outdated, or plan-mismatched consent and filters execution to Safe/Low suggestions that support Recycle Bin. |

## Known limits and follow-up actions

1. **Final path races:** permanent directory traversal is handle-bound, but Recycle Bin operations and individual file deletion still cross a final path-based Windows shell/filesystem API boundary. Expected snapshots and postchecks reduce the window; fully closing it would require a handle-native design for every deletion mode.
2. **Program-leftover staleness:** a reviewed leftover directory can receive new files between analysis and execution. Current mitigation is conservative policy: disabled, unselected, high-risk, descendant-recency checked, and Recycle-Bin-only. A future directory-manifest snapshot could fail closed on repopulation.
3. **Scanner adversarial swaps:** managed scanning resolves and rechecks link targets but still uses Core path enumeration. Turbo strongly locks root ancestry where Windows permits; ACL/sharing-protected ancestors and queued descendants retain narrow same-privilege swap windows. Persisted identity and downstream snapshot/no-follow deletion prevent stale rows from silently authorizing changed-file deletion.
4. **Ambiguous SQLite commit acknowledgement:** folder aggregation uses additive upsert. An extremely narrow “commit succeeded but async call threw” retry could double direct metrics. Idempotent batch IDs or replacement semantics would close this.
5. **SQLite wait cancellation:** cross-process writer acquisition is bounded by 30 seconds, but the underlying immediate transaction acquisition cannot cooperatively observe cancellation while SQLite is blocked.
6. **UI interaction coverage:** Results, Duplicates, Cleanup, Scan, Space Map, Dashboard/Workspace, and Settings lifecycle fixes compile cleanly but lack a non-WinUI ViewModel harness. Real startup verification does not prove every navigation/filter/error timing permutation.
7. **Environment matrix:** clean-machine install/upgrade, Authenticode signing, Windows 10 build matrix, ARM64, diverse drive-health hardware, network filesystems, and fault-injection power-loss tests remain release/lab work.
8. **Quarantine crash interval:** transactional and fallback writes cover database failures, but process/power loss after a filesystem move and before either write can require manual reconciliation of the quarantine directory and planned journal entry.
9. **Installer compiler:** Inno Setup compilation cannot be claimed on a machine without the compiler. Workflow/script validation is not an installed-product smoke test.
10. **Cleanup analysis completeness:** `CleanupEngine.GetSuggestionsAsync()` logs and isolates a rule exception so later rules still run, but its return type has no partial-analysis warning channel. An empty/missing suggestion therefore does not by itself prove that every enabled rule completed; a future result envelope should expose rule failures to the UI/CLI.

## Release decision rule

Do not call this source release-ready unless all of the following are current and green: Release restore/format/build, complete .NET suite with the required real Turbo binary, Rust format/lint/test/release build/audit, dependency vulnerability checks, workflow/release-script validation, x64 WinUI launch with a responsive top-level window, installer compilation, and clean-machine install/update smoke tests. Any unavailable gate must remain explicitly unverified.
